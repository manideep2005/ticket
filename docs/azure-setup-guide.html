Step 0 Before you start

Ten minutes of checking now prevents a rebuild later — especially the region choice, because Cosmos DB, Service Bus, Functions and email are not available in every region.

0.1 Confirm your subscription
2 min
  • Portal → Subscriptions. You want Azure for Students (or pay-as-you-go) in Active state.
  • Note the Subscription ID and the Offer type — the free-tier toggle for Cosmos depends on the offer.
  • Check the remaining credit balance. Azure for Students gives a fixed credit and does not auto-charge a card — when credit ends, resources stop.
✔ Collect: Subscription ID ✔ Collect: subscription name / offer type 
az login
az account show --query "{id:id, name:name, offer:user.assignedTo}" -o json
az account list -o table
0.2 Pick ONE region and stick to it
2 min
  • Recommended: East US or Central India — broadly available for Cosmos, Service Bus, Functions and email.
  • Everything (resource group, Cosmos, Service Bus, Functions, Insights) goes in the same region: fewer latency surprises, simpler quota maths.
  • Communication Services email has its own data location setting (separate from region) — decided in step 8.
✔ Collect: chosen region code (e.g. eastus)
0.3 Install the CLI (faster than clicking)
5 min

You can do every step in the portal instead — the CLI is only to save time.

# macOS
brew install azure-cli
az version

# Azure Functions Core Tools (needed later to run the API locally)
brew tap azure/functions && brew install azure-functions-core-tools@4
ℹ️
Only the Azure CLI and a browser are required tonight. The Functions tools are needed when we write and deploy the API.

Step 2 Cosmos DB — the ticket database

One account, one database, four containers. This is where tickets, messages, audit entries and idempotency records live.

2.1 Create the Cosmos DB account (NoSQL / Core SQL API)
10–15 min
  • Portal → Azure Cosmos DB → Create → Azure Cosmos DB for NoSQL.
  • Capacity mode: try the Free tier discount toggle. If your offer does not allow it, choose Serverless — cheapest for a project with bursty, low traffic. (Provisioned 400 RU/s costs roughly $24/month and will eat student credit.)
  • Consistency: Session. Geo-redundancy: off. Backup: periodic default.
  • Name must be globally unique and lowercase: cosmos-support-dev-<yourinitials>.
# Serverless variant (recommended if free tier is unavailable)
az cosmosdb create -n cosmos-support-dev-mg -g $RG \
  --locations regionName=$LOC failoverPriority=0 isZoneRedundant=false \
  --default-consistency-level Session \
  --capabilities EnableServerless

# Free-tier variant (only if your offer supports it)
# add: --enable-free-tier true
✔ Collect: Cosmos account name ✔ Collect: account endpoint URI (https://…documents.azure.com:443/) 
az cosmosdb show -n cosmos-support-dev-mg -g $RG \
  --query "{name:name, endpoint:documentEndpoint}" -o json
2.2 Create database supportplatform and four containers
8 min

Partition keys must be chosen before data exists — these match the field names the UI already sends:

ContainerPartition keyHolds
tickets/customerIdTicket documents (status, priority, assignment, timestamps)
messages/ticketIdConversation messages for a ticket
audit/tenantIdWho changed what, when (needed for disputes & later multi-tenant work)
idempotency/idRequest-key → response cache so retries never duplicate tickets (set TTL on)
 
ACC=cosmos-support-dev-mg
az cosmosdb sql database create -a $ACC -g $RG -n supportplatform

az cosmosdb sql container create -a $ACC -g $RG -d supportplatform -n tickets     -p /customerId
az cosmosdb sql container create -a $ACC -g $RG -d supportplatform -n messages    -p /ticketId
az cosmosdb sql container create -a $ACC -g $RG -d supportplatform -n audit       -p /tenantId
az cosmosdb sql container create -a $ACC -g $RG -d supportplatform -n idempotency -p /id \
  --ttl 86400
⚠️
Do not collect the Cosmos key. We will use managed identity (step 5), so the endpoint plus names is all that is needed. If managed identity is not possible for local development, you can keep the key in local.settings.json on your machine — never send it.
= Database name: supportplatform = Containers: tickets, messages, audit, idempotency

Step 3 Service Bus — automatic routing queue

Ticket creation publishes a message here; a queue-triggered function consumes it and assigns the team. Creating the queue alone is not the feature — the function is.

3.1 Create namespace + queue ticket-routing
6 min
  • Namespace name: sb-support-dev-<yourinitials> (globally unique).
  • Pricing tier: Basic is the cheapest and works if we implement duplicate-safety in the function (the roadmap requires idempotent processing anyway). Standard (≈ $10/month) adds built-in duplicate detection — pick Standard only if you want that native feature.
  • Queue settings: max delivery count 10, dead-lettering on message expiration on, duplicate detection 10 min (Standard tier only).
SB=sb-support-dev-mg
az servicebus namespace create -n $SB -g $RG --sku Basic

az servicebus queue create -n ticket-routing \
  --namespace-name $SB -g $RG \
  --max-delivery-count 10 --enable-dead-lettering-on-message-expiration true

# Standard tier only:
# --enable-duplicate-detection true --duplicate-detection-history-time-window PT10M
✔ Collect: namespace name ✔ Collect: fully-qualified namespace (sb-support-dev-mg.servicebus.windows.net) ✔ Collect: queue name (ticket-routing) ✖ Do NOT send: connection string

Step 4 Function App + Application Insights

The API and the queue processor run here. Application Insights is created along with it and gives the monitoring evidence the roadmap asks for (FR-09).

4.1 Create a storage account for the Functions runtime
3 min

Name must be globally unique, 3–24 lowercase letters/digits: stsupportdev<initials>.

ST=stsupportdevmg
az storage account create -n $ST -g $RG -l $LOC --sku Standard_LRS --kind StorageV2
4.2 Create the Function App (Node, Consumption, Linux)
5 min

Portal equivalent: Function App → Create → Consumption plan → runtime stack Node.js 20 (or 22 if offered) → Linux → same region → new App Insights.

FN=func-support-dev-mg
az functionapp create -n $FN -g $RG \
  --consumption-plan-location $LOC \
  --runtime node --runtime-version 20 --functions-version 4 \
  --os-type Linux \
  --storage-account $ST
✔ Collect: function app name ✔ Collect: default hostname (func-support-dev-mg.azurewebsites.net)

Step 5 Managed identity + role assignments

This is the step that lets the whole system run with no keys anywhere. Do it now — retrofitting identity later is what forces connection strings into code.

5.1 Turn on the Function App's system-assigned identity
2 min

Portal → Function App → Identity → System assigned → On. The CLI returns the identity's principal ID.

az functionapp identity assign -n $FN -g $RG
PRINCIPAL_ID=$(az functionapp identity show -n $FN -g $RG --query principalId -o tsv)
echo $PRINCIPAL_ID
5.2 Grant it least-privilege access to Cosmos, Service Bus and Insights
6 min 
# Cosmos DB — data plane (Data Contributor)
az cosmosdb sql role assignment create \
  --account-name $ACC -g $RG --scope "/" \
  --role-definition-id 00000000-0000-0000-0000-000000000002 \
  --principal-id $PRINCIPAL_ID

# Service Bus — send + receive on the namespace
SB_ID=$(az servicebus namespace show -n $SB -g $RG --query id -o tsv)
az role assignment create --assignee $PRINCIPAL_ID \
  --role "Azure Service Bus Data Owner" --scope $SB_ID

# Application Insights — publish telemetry
AI_ID=$(az monitor app-insights component show --app appi-support-dev-mg -g $RG --query id -o tsv)
az role assignment create --assignee $PRINCIPAL_ID \
  --role "Monitoring Metrics Publisher" --scope $AI_ID
✅
Also grant yourself the same roles. Then local development works with az login + DefaultAzureCredential — you never handle a Cosmos key, and there is nothing secret to send me.
MY_ID=$(az ad signed-in-user show --query id -o tsv)
az cosmosdb sql role assignment create --account-name $ACC -g $RG --scope "/" \
  --role-definition-id 00000000-0000-0000-0000-000000000002 --principal-id $MY_ID
az role assignment create --assignee $MY_ID --role "Azure Service Bus Data Owner" --scope $SB_ID

Step 7 Entra ID — accounts, roles, app registration

Two separate concerns: who signs in to the portal (handled in 6.2) and how the API verifies identity. This step collects the IDs the backend needs — and no secrets.

7.1 Record your tenant details
2 min 
az account show --query "{tenantId:tenantId, tenant:tenantDisplayName}" -o json

✔ Collect: tenant ID (GUID) ✔ Collect: tenant domain (name.onmicrosoft.com or custom)
7.2 Create the API app registration with scopes and roles
10 min

Portal → Microsoft Entra ID → App registrations → New registration: name support-platform-api, supported accounts = Accounts in this organizational directory only (for now). Then:

  • Expose an API → Application ID URI: api://<client-id>.
  • Add scopes: tickets.read, tickets.write, tickets.admin.
  • App roles → create Customer, Agent, Admin (member type: Users/Groups).
  • Do not create a client secret yet. When the time comes (deployed backend calling other services) we use managed identity instead.
az ad app create --display-name support-platform-api
# then in the portal: Expose an API → add scopes, and App roles → add Customer/Agent/Admin
✔ Collect: API app registration client ID (application ID) ✔ Collect: Application ID URI (api://…) ✔ Collect: names of scopes and app roles created ✖ Do NOT create/send: client secret
7.3 Create one test account per role
6 min

Portal → Microsoft Entra ID → Users → New user → create user: agent1@<yourdomain> and admin1@<yourdomain> (plus your own account as customer). Assign roles: Enterprise applications → support-platform-api → Users and groups.

⚠️
These are real directory accounts. Use a strong generated password, and do not use these credentials as the application's authentication mechanism — the app always signs you in through Entra, never against a hardcoded password (roadmap FR-07).
✔ Collect: list of test account email addresses (no passwords) ✔ Collect: which role each account was assigned
7.4 Protect your administrators (5 minutes that matter)
5 min
  • Ensure at least one break-glass admin account exists with a documented long password and no MFA dependency.
  • Require MFA for administrators (Entra ID Free tier supports security defaults / per-user MFA).
  • Never use a personal Microsoft account as an app owner.

Step 8 Email notifications (Azure Communication Services)

Ticket created / assigned / resolved notifications. This step can be skipped tonight without blocking anything — email is Phase 7 of the roadmap and the app runs without it.

8.1 Create the ACS resource and an Email Communication Service
10 min
  • Portal → Communication Services → Create → name acs-support-dev, pick a data location (United States / Europe / Asia Pacific — this is separate from your Azure region and cannot be changed later).
  • Then → Email → Email Communication Services → Create → same data location.
  • Domains → Add domain → Azure Managed Domain. This gives you a free sending domain (xxxxx.azurecomm.net) for testing without owning DNS.
  • Wait for domain status to become Verified / Ready, then Connect the domain to the ACS resource.
✔ Collect: ACS resource name ✔ Collect: sender address (DoNotReply@<xxxxx>.azurecomm.net) ✔ Collect: chosen email data location ✖ Do NOT send: ACS connection string
ℹ️
A custom domain (e.g. support@yourdomain.com) needs DNS records (SPF, DKIM, domain verification). Do that later; the managed domain is enough to prove a real email was delivered.
